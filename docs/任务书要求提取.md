# 人脸比对系统：技术实现要求

> 任务书来源：[智能科学综合实践任务书.docx](/home/leo/camera-face-comparison/docs/智能科学综合实践任务书.docx)
> 本文件用于后续需求分析、系统设计、测试和展示的技术基线。

## 1. 项目目标与边界

开发一个基于外置摄像头的人脸比对系统，完成从实时图像采集、人脸检测、特征提取、特征比对到可视化结果输出的完整闭环。

- 实现语言/框架方向：Python + 人工智能/计算机视觉开发框架。
- 运行形态不预先锁定：可以直接以 Python 程序运行，也可以在后续技术路线中打包成 EXE；这是展示与部署方式的选择，不是功能歧义。
- 系统应具备可展示性、稳定的完整流程，并体现一定的设计特色或创新点。

## 1.1 课程开发过程要求

任务书要求按照完整的工程开发流程组织实践：

1. 阅读任务书、查阅文献并了解问题背景和相关技术；
2. 对问题进行需求分析，分析数据、划分功能并明确人机交互需求；
3. 根据需求进行系统设计，明确主要模块和算法；
4. 按照设计编写程序、完成调试并解决软硬件适配问题；
5. 对程序进行功能测试；
6. 针对测试中发现的问题实施优化，重新测试并分析性能改善结果；
7. 对实现结果进行合理分析和解释，形成课程设计总结。

开发过程中应根据实验现象和测试结果动态调整实验方案，并保留“问题发现—原因分析—方案实施—复测对比”的过程证据。

## 2. 必须实现的基础功能

| 编号 | 技术要求 | 任务书标注分值 | 最低验收结果 |
|---|---|---:|---|
| F-01 | 调用外置摄像头，实时采集图像并支持拍照。 | 10% | 能正确打开指定外置摄像头，界面显示实时画面，并能抓拍图像。 |
| F-02 | 建立人脸标准库。 | 15% | 标准库至少包含 3 名不同人员，并能作为后续识别的基准数据源。 |
| F-03 | 完成人脸比对判别。 | 40% | 待测人脸与标准库匹配成功时输出对应姓名；不匹配时输出“未知人员”。 |
| F-04 | 提供系统 UI，并优化界面布局与视觉设计。 | 10% | 能通过界面完成标准库管理、摄像头采集和比对等主要操作；界面简洁、美观，画面和结果清晰，操作友好。 |
| F-05 | 支持标准库动态扩容。 | 5% | 用户可以新增人员和人脸样本；新增内容能参与后续比对。 |

基础功能（F-01 至 F-05）是系统必须首先完成的主链路。

## 3. 标准人脸库的数据要求

### 3.1 人员数量

- 最少录入 3 名不同人员。
- 每名人员应具备唯一的人员标识和展示名称。

### 3.2 样本数量与采集方式

任务书没有规定每名人员的最低样本数量、指定姿态或固定采集顺序。因此这些内容不能作为课程硬性验收条件。

当前项目采用以下最低可用规则：

- 每名人员至少有 1 张通过检测和质量检查的图片，首张有效样本即可参与识别。
- 图片既可以来自外置摄像头抓拍，也可以从本地文件导入。
- 单张录入图片只接受 1 张可信人脸；无人脸、多人脸、脸过小或明显模糊时拒绝入库并给出原因。
- 标准库保存人员、样本图片、特征向量及其对应关系。

### 3.3 多样本能力的定位

同一人员允许继续追加多张不同质量、角度或来源的图片，但多样本是提高稳定性和开展优化实验的手段，不是人员入库条件，也不是任务书规定的固定动作流程。是否采用样本聚合、质量加权或人员模板，应通过后续同集实验决定。

## 4. 核心处理链路

系统至少包含以下相互衔接的模块；算法、模型和具体库在技术路线阶段确定，不被任务书锁死。

```text
外置摄像头实时画面
  → 图像抓拍与预处理
  → 人脸检测与质量校验
  → 人脸对齐/裁剪（如模型需要）
  → 特征向量提取
  → 与标准库多样本特征进行相似度比对
  → 阈值判定：人员姓名 / 未知人员
  → UI 可视化与日志记录
```

### 4.1 图像采集与预处理

- 调用外置摄像头接口，读取实时视频帧并完成抓拍。
- 统一图像输入规格；可进行尺寸归一化和颜色空间转换。
- 对无法打开摄像头、读取帧失败等情况提供明确提示和恢复路径。

### 4.2 人脸检测与质量校验

- 定位图像中的人脸区域，过滤无效背景和非人脸干扰。
- 检查人脸数量；标准库录入阶段默认只接受单人脸图像。
- 对检测失败、多人脸、过小人脸或明显模糊等异常情况给出可理解的 UI 提示。
- 可使用 MTCNN、RetinaFace 或其他适配本机环境的检测方案；任务书列举的模型仅为参考。

### 4.3 特征提取与人员表示

- 将标准库样本和待测人脸转换为可比较的人脸特征向量。
- 可使用 FaceNet、ArcFace 或其他预训练人脸识别模型；任务书列举的模型仅为参考。
- 系统至少能保存并比较人员样本的特征向量；可进一步支持同一人员多样本及人员聚合表示。

### 4.4 比对、阈值与未知人员判定

- 使用余弦相似度、欧式距离或等价方法计算待测人脸与标准库的匹配程度。
- 系统必须支持配置或调整判定阈值。
- 达到阈值时，输出最高匹配人员的姓名与相似度；未达到阈值时，输出“未知人员”。
- 阈值应通过实际样本测试确定，并在优化过程中根据误识别、拒识或速度问题进行调整。

### 4.5 UI 与结果输出

- 显示实时摄像头画面。
- 显示检测到的人脸框或等价视觉反馈。
- 显示相似度数值及最终判定结果。
- 显示匹配人员姓名或“未知人员”。
- 支持从 UI 新增人员和人脸样本，并将其用于后续比对。
- 建议记录抓拍时间、匹配结果、相似度和异常原因，便于测试、优化和现场展示。

## 5. 扩展功能加分项与优化过程

任务书把扩展功能单列为加分项，并要求开发过程体现“测试发现问题 → 优化 → 再测试验证”。基础功能应先完成；为了取得扩展分数，项目再选择能力和时间范围内能够完整实现、复测和讲清楚的一项或多项优化。任务书列举的困难场景是选题方向，不等于要求一个课设同时解决全部问题。

### 5.1 为取得扩展分数，至少完成一项可展示的优化

可以自行设计实现，最终向老师展示。可选方向包括但不限于：

- 人脸检测鲁棒性优化（10%）：改善侧脸、局部遮挡（口罩/眼镜）、暗光、曝光等特殊条件下的人脸检测效果。
- 人脸检测与比对时间优化（10%）：针对实际测试结果缩短从抓拍到输出比对结果的处理时间。
- 标准库优化：改进多样本特征聚合、样本质量筛选、增量录入或阈值自适应策略。
- 交互与可视化优化：增加结果历史、相似度排序、采样质量提示、实时状态反馈等有明确技术价值的功能。

### 5.2 优化必须可对比验证

每次优化至少保留以下可复现证据：

1. 优化前版本的测试场景、指标和结果；
2. 发现的问题及原因分析；
3. 具体优化措施；
4. 优化后在相同或等价条件下的测试结果；
5. 前后对比结论，以及优化带来的收益和代价。

可根据优化方向选择指标：

- 准确性：已知人员正确识别率、未知人员拒识率、误识别次数；
- 鲁棒性：不同姿态、光照、遮挡条件下的检测成功率/识别正确率；
- 性能：单次比对耗时、平均耗时、帧率或端到端响应时间；
- 可用性：录入成功率、异常提示是否可理解、动态扩容后是否立即生效。

## 6. 代码工程化要求

- 源码按模块拆分，不把全部逻辑堆放在单一源文件中。
- 变量使用描述性命名，做到见名知意。
- 函数使用统一注释，说明功能、输入、输出和必要条件。
- 关键处理步骤添加注释，特别是摄像头调用、样本校验、特征生成、阈值判定和数据持久化逻辑。
- 模块之间通过清晰的数据接口协作，保证采集、检测、特征、标准库、比对和 UI 可以独立调试。

## 7. 展示与验收要求

- 在实践课内向指导老师或助教演示程序；
- 能解释程序的主要模块、数据流和算法；
- 能回答与实现方案、测试结果和优化过程有关的问题；
- 验收时应能够说明实际运行条件、已完成的基础功能、扩展功能以及尚未解决的局限性。

## 8. 范围说明

本文件只提取与技术实现、工程开发和程序验收直接相关的要求。报告排版、纸质打印、提交截止时间、提交文件夹命名等提交管理事项不纳入本文件；程序源代码、工程文件和操作说明仍应按课程要求单独整理。
