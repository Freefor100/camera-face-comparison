# 人脸比对系统：技术实现要求

> 任务书来源：[智能科学综合实践任务书.docx](/home/leo/camera-face-comparison/docs/智能科学综合实践任务书.docx)
> 本文件用于后续需求分析、系统设计、测试和展示的技术基线。

## 1. 项目目标与边界

开发一个基于外置摄像头的人脸比对系统，完成从实时图像采集、人脸检测、特征提取、特征比对到可视化结果输出的完整闭环。

- 实现语言/框架方向：Python + 人工智能/计算机视觉开发框架。
- 运行形态不预先锁定：可以直接以 Python 程序运行，也可以在后续技术路线中打包成 EXE；这是展示与部署方式的选择，不是功能歧义。
- 系统应具备可展示性、稳定的完整流程，并体现一定的设计特色或创新点。

## 2. 必须实现的基础功能

| 编号 | 技术要求 | 任务书标注分值 | 最低验收结果 |
|---|---|---:|---|
| F-01 | 调用外置摄像头，实时采集图像并支持拍照。 | 10% | 能正确打开指定外置摄像头，界面显示实时画面，并能抓拍图像。 |
| F-02 | 建立人脸标准库。 | 15% | 标准库至少包含 3 名不同人员，并能作为后续识别的基准数据源。 |
| F-03 | 完成人脸比对判别。 | 40% | 待测人脸与标准库匹配成功时输出对应姓名；不匹配时输出“未知人员”。 |
| F-04 | 提供系统 UI。 | 10% | 能通过界面完成标准库管理、摄像头采集和比对等主要操作；画面和结果清晰、操作友好。 |
| F-05 | 支持标准库动态扩容。 | 5% | 用户可以新增人员和人脸样本；新增内容能参与后续比对。 |

基础功能（F-01 至 F-05）是系统必须首先完成的主链路。

## 3. 标准人脸库的数据要求

### 3.1 人员数量

- 最少录入 3 名不同人员。
- 每名人员应具备唯一的人员标识和展示名称。

### 3.2 初始样本数量与采集规范

任务书只规定至少 3 名人员，不规定每人的样本数。为避免“单张照片比对”导致姿态、光照变化下结果不稳定，采用以下实现基线：

- 每名人员初始录入 **至少 5 张有效样本**，因此初始标准库至少 15 张有效样本。
- 5 张样本分别覆盖：正脸、向左转脸、向右转脸、轻度抬头、轻度低头。
- 每张样本只允许出现 1 张可用人脸；检测到多张人脸、无人脸或图像明显模糊时，提示重新采集。
- 标准库应保存“人员—样本/特征向量”的对应关系；同一人员的多张样本共同参与比对，而不是只保留单张人脸图像。

这一基线参考当前人脸库的通用做法：官方文档建议为同一人员存储多张不同姿态图像，并明确建议至少 5 张；多张人脸特征向量可聚合为该人员的表示，从而增强不同光照、姿态和清晰度条件下的匹配稳定性。[Amazon Rekognition 采集建议](https://docs.aws.amazon.com/rekognition/latest/dg/recommendations-facial-input-images-search.html) 与 [Amazon Rekognition 人脸库说明](https://docs.aws.amazon.com/rekognition/latest/dg/collections.html)；Python `face_recognition` 的官方示例也提供了“每人多张图片”训练与识别方式。[官方示例索引](https://github.com/ageitgey/face_recognition)

## 4. 核心处理链路

系统至少包含以下相互衔接的模块；算法、模型和具体库在技术路线阶段确定，不被任务书锁死。

```text
外置摄像头实时画面
  → 图像抓拍与预处理
  → 人脸检测与质量校验
  → 人脸对齐/裁剪（如模型需要）
  → 特征向量提取
  → 与标准库多样本特征进行相似度比对
  → 阈值判定：人员姓名 / 未知人员
  → UI 可视化与日志记录
```

### 4.1 图像采集与预处理

- 调用外置摄像头接口，读取实时视频帧并完成抓拍。
- 统一图像输入规格；可进行尺寸归一化和颜色空间转换。
- 对无法打开摄像头、读取帧失败等情况提供明确提示和恢复路径。

### 4.2 人脸检测与质量校验

- 定位图像中的人脸区域，过滤无效背景和非人脸干扰。
- 检查人脸数量；标准库录入阶段默认只接受单人脸图像。
- 对检测失败、多人脸、过小人脸或明显模糊等异常情况给出可理解的 UI 提示。
- 可使用 MTCNN、RetinaFace 或其他适配本机环境的检测方案；任务书列举的模型仅为参考。

### 4.3 特征提取与人员表示

- 将标准库样本和待测人脸转换为可比较的人脸特征向量。
- 可使用 FaceNet、ArcFace 或其他预训练人脸识别模型；任务书列举的模型仅为参考。
- 同一人员应保留多张样本的特征向量，或生成稳定的人员聚合特征；不能仅依赖单张基准图像。

### 4.4 比对、阈值与未知人员判定

- 使用余弦相似度、欧式距离或等价方法计算待测人脸与标准库的匹配程度。
- 系统必须支持配置或调整判定阈值。
- 达到阈值时，输出最高匹配人员的姓名与相似度；未达到阈值时，输出“未知人员”。
- 阈值应通过实际样本测试确定，并在优化过程中根据误识别、拒识或速度问题进行调整。

### 4.5 UI 与结果输出

- 显示实时摄像头画面。
- 显示检测到的人脸框或等价视觉反馈。
- 显示相似度数值及最终判定结果。
- 显示匹配人员姓名或“未知人员”。
- 支持从 UI 新增人员和人脸样本，并将其用于后续比对。
- 建议记录抓拍时间、匹配结果、相似度和异常原因，便于测试、优化和现场展示。

## 5. 扩展与优化过程要求

课程要求不仅是实现功能，还必须体现“测试发现问题 → 优化 → 再测试验证”的过程。该过程是本项目的硬性技术要求。

### 5.1 至少完成一项可展示的扩展/优化

可以自行设计实现，最终向老师展示。可选方向包括但不限于：

- 鲁棒性优化：改善侧脸、口罩/眼镜遮挡、暗光、逆光、曝光或轻度模糊情况下的检测与识别效果。
- 速度优化：缩短从抓拍到输出比对结果的时间。
- 标准库优化：改进多样本特征聚合、样本质量筛选、增量录入或阈值自适应策略。
- 交互与可视化优化：增加结果历史、相似度排序、采样质量提示、实时状态反馈等有明确技术价值的功能。

### 5.2 优化必须可对比验证

每次优化至少保留以下可复现证据：

1. 优化前版本的测试场景、指标和结果；
2. 发现的问题及原因分析；
3. 具体优化措施；
4. 优化后在相同或等价条件下的测试结果；
5. 前后对比结论，以及优化带来的收益和代价。

可根据优化方向选择指标：

- 准确性：已知人员正确识别率、未知人员拒识率、误识别次数；
- 鲁棒性：不同姿态、光照、遮挡条件下的检测成功率/识别正确率；
- 性能：单次比对耗时、平均耗时、帧率或端到端响应时间；
- 可用性：录入成功率、异常提示是否可理解、动态扩容后是否立即生效。

## 6. 代码工程化要求

- 源码按模块拆分，不把全部逻辑堆放在单一源文件中。
- 变量使用描述性命名，做到见名知意。
- 函数使用统一注释，说明功能、输入、输出和必要条件。
- 关键处理步骤添加注释，特别是摄像头调用、样本校验、特征生成、阈值判定和数据持久化逻辑。
- 模块之间通过清晰的数据接口协作，保证采集、检测、特征、标准库、比对和 UI 可以独立调试。

## 7. 技术验收清单

- [ ] 可调用外置摄像头，实时显示并抓拍图像。
- [ ] 已建立至少 3 名人员、每人至少 5 张有效样本的标准库。
- [ ] 能录入新人员/新样本，且新增内容可在后续比对中被识别。
- [ ] 已知人员可输出正确姓名和相似度。
- [ ] 未录入人员可稳定输出“未知人员”。
- [ ] UI 显示画面、人脸反馈、相似度和最终结论。
- [ ] 对检测失败、多人脸、无脸、低质量样本和摄像头异常有处理或提示。
- [ ] 至少完成一项自研扩展/优化。
- [ ] 已保留优化前后可对比的测试数据、结果和结论。
- [ ] 源码模块化，关键函数和关键处理步骤有规范注释。
