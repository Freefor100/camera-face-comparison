# 标准库精确矩阵检索 CPU/CUDA 基准实验

本文只计算“已经取得待识别人脸特征向量后，从标准库找到前两名候选”所需的时间。
数据角色和耗时统计定义见 [术语与内部命名](术语与内部命名.md)。

## 1. 实验问题

当前桌面识别服务每次查询都会从 SQLite 读取样本、按人员重新分组、重新计算人员平均
特征向量，再通过 Python 循环逐人计算分数和完整排序。本实验只回答三个问题：

1. 提前计算人员平均特征向量并组成连续矩阵，能否加速候选检索；
2. 每次只识别一张图片时，是否值得把候选检索放到 CUDA；
3. 是否值得在 SQLite 中额外保存人员平均特征向量。

实验不修改人脸模型、聚合公式、阈值或独立验证集结果，也不把图片解码、人脸推理、
完整性扫描和日志写入时间混入检索数字。

## 2. 数据与环境

- 数据：阶段 4 固定的自然 LFW 协议；标准库包含 4,599 个身份、7,490 张参考图片；
- 有效数据：4,588 个身份、7,465 个标准库人脸特征向量、5,720 个有效待识别图片特征向量；
- 待识别向量：固定种子 `2026` 选择 200 个不同的真实 LFW 待识别图片；
- 当前实现因重复计算开销较大，每个规模抽取其中 30 个待识别向量计时；
- 向量格式：InsightFace `buffalo_l` 产生的 512 维 `float32` L2 单位向量；
- CPU：Intel Core i5-12500H；NumPy 2.5.2；OpenBLAS 0.3.34，默认 16 线程；
- GPU：NVIDIA GeForce RTX 3050 Laptop GPU，4,096 MiB；驱动 610.57.04；
- CUDA 路径：ONNX Runtime 1.29 的矩阵乘法和前两名选择算子（`MatMul + TopK`）；
  人员平均特征向量矩阵作为模型常量常驻显存，每个待识别向量从 CPU 上传，只把前两名
  分数和位置传回 CPU。

人员平均特征向量矩阵共有 P 行、512 列，记作 `P×512`。P 表示有效标准库身份数，每一行
对应一名人员的 512 维平均特征向量。

每个实现先运行 10 次但不计入结果，再逐个待识别向量同步计时。CPU 矩阵另外测试单线程；
表中采用实际更快的 OpenBLAS 默认 16 线程结果。ONNX Runtime 的性能跟踪记录确认，
`MatMul` 和 `TopK` 两个计算节点确实在 `CUDAExecutionProvider` 上执行，而不是只在
“可用后端”列表中显示 CUDA。

## 3. 被比较的实现

| 对照方法 | 每次识别执行的工作 |
| --- | --- |
| 当前运行路径 | 重新归一化全部样本、按身份计算人员平均特征向量、逐人点积、完整排序和阈值判定 |
| 提前计算人员表示后逐人比较 | 人员平均特征向量只计算一次，但仍通过 Python 循环逐人点积并取前两名 |
| CPU 全量精确矩阵检索 | `prototype_matrix @ query` 表示“人员平均特征向量矩阵乘以待识别向量”；一次得到全部人员分数，再用部分排序取前两名 |
| CUDA 全量精确矩阵检索 | GPU 执行 `MatMul + TopK`；包含单个输入上传和前两名结果下载 |

CPU 矩阵与当前运行路径在每个规模抽查 10 个待识别向量，共 50 次；第一候选身份全部
一致，前两名分数最大绝对误差为 `1.1921e-7`。CUDA 与 CPU 的首个待识别向量第一候选
全部一致，最大分数误差不超过 `5.9605e-8`。这些误差来自 `float32` 运算顺序，不影响
当前阈值判定。

## 4. 单次候选检索延迟

单位均为毫秒。“延迟中位数（p50）”表示一半查询不超过该时间；“95% 分位延迟
（p95）”表示 95% 的查询不超过该时间。加速比使用当前运行路径的延迟中位数除以 CPU
全量精确矩阵检索的延迟中位数。

| 身份数 | 样本数 | 当前路径 p50 / p95 | 提前计算后逐人比较 p50 | CPU 精确检索 p50 / p95 | CUDA 精确检索 p50 / p95 | CPU 加速比 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 3 | 6 | 0.0396 / 0.1516 | 0.0079 | 0.0058 / 0.0063 | 0.0579 / 0.0642 | 6.80× |
| 10 | 20 | 0.1155 / 0.1261 | 0.0126 | 0.0060 / 0.0064 | 0.0447 / 0.0522 | 19.30× |
| 100 | 165 | 1.0488 / 1.1282 | 0.0665 | 0.0087 / 0.0090 | 0.0468 / 0.0567 | 120.83× |
| 1,000 | 1,642 | 10.9741 / 11.6739 | 0.6452 | 0.0204 / 0.0442 | 0.0859 / 0.0984 | 537.91× |
| 4,588 | 7,465 | 50.8554 / 53.5888 | 3.1706 | 0.0524 / 0.1301 | 0.1312 / 0.1487 | 971.34× |

完整 LFW 规模的人员平均特征向量矩阵占 `9,396,224` 字节，约 8.96 MiB，只占 4 GiB
显存的约 0.22%，因此显存容量不是问题。CUDA 较慢的原因是单次识别工作量较小，同时必须
承担输入上传、输出下载和 CUDA 计算任务启动；GPU 的并行计算没有抵消这些固定成本。完整规模
CUDA 延迟中位数是最快 CPU 的 2.50 倍，即延迟更高而不是获得加速。

第一个 CUDA 计算会话的初始化耗时为 300.60 ms；CUDA 运行库已经加载后，其余不同规模
会话的构建耗时为 2.20～7.78 ms。ONNX Runtime 还提示环境未安装 `libcufft.so.12`；
本实验使用的算子不依赖快速傅里叶变换（FFT），性能跟踪记录也确认 `MatMul/TopK` 在
CUDA 上执行，但这不代表本机 CUDA 运行库的所有可选组件均已安装。

## 5. 启动构建与持久化结果

完整有效标准库的实测启动工作为：

| 操作 | 耗时 |
| --- | ---: |
| 从 SQLite 读取 7,465 个标准库人脸特征向量 | 30.90 ms |
| 计算 4,588 个人员平均特征向量并构建连续矩阵 | 59.22 ms |
| 保存预计算 `.npy` 矩阵 | 2.10 ms |
| 同一进程、受操作系统页缓存影响的 `.npy` 加载 | 1.53 ms |

从样本恢复完整矩阵合计约 90.12 ms。预计算矩阵确实能缩短这一次启动工作，但 1.53 ms
是同一进程页缓存结果，不是严格冷启动数据。即使按该数字计算，节省的也只是启动时约
90 ms，却要额外处理原始样本与派生平均向量的一致性、聚合公式版本、模型版本和事务更新。
因此当前规模不把人员平均特征向量作为第二份事实写入 SQLite；启动时从原始人脸特征向量
重建更简单、可靠。

## 6. 结论与下一步边界

1. **CPU 全量精确矩阵检索方案成立。**它保持精确分数和候选不变，并在大型标准库中
   消除重复人员表示计算、Python 循环和完整排序；不需要 Faiss、红黑树或近似向量索引。
2. **当前单次识别不采用 CUDA 检索。**本机所有测试规模下默认 OpenBLAS CPU 均更快；
   CUDA 继续用于耗时远高于检索的人脸检测和人脸特征向量推理。
3. **当前不额外保存人员平均特征向量。**完整 LFW 规模启动重建不足 0.1 秒，节省的启动
   时间不足以抵消派生数据的一致性维护成本。
4. **最终少量身份演示的绝对收益很小。**3～10 人只节省约 0.04～0.11 ms，不能作为
   端到端时间优化成果；完整 LFW 规模则能节省约 50.80 ms，说明它是明确的可扩展性优化。
5. 若接入桌面程序，应增加一个内存标准库检索结构：启动时完成一次完整性检查并构建矩阵，
   识别时只执行 CPU 全量精确矩阵检索；人员创建或追加样本成功后，只重建受影响人员的
   平均特征向量。接入后还要做包含人脸推理、完整性检查、判定和日志写入的完整链路对照，
   不能用本次单独测量的候选检索时间代替系统总耗时。
