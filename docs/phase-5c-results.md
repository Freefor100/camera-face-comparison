# 阶段 5C：运行时性能、多帧方法与界面验收

本文记录阶段 5C 已实际完成的工作和证据。阶段 5B 已经冻结了人员平均特征向量、最高分阈值和
`minimum_score = 0.5557855367660522`；本阶段没有重新调参，也没有把最终演示人员加入标准库。

## 1. 本阶段结论

1. 运行时已接入内存中的人员平均特征矩阵。启动时做一次完整性检查并从 SQLite 样本构建矩阵，
   查询时直接做 CPU 精确矩阵乘法；录入成功后只刷新受影响人员对应的标准库行。
2. 与“每次识别都读 SQLite、重新求平均、用 Python 逐人比较”的基线相比，标准库达到 1,000 和
   4,588 个身份时，完整识别链路的延迟明显下降；3、10、100 个身份的小库收益很小，不能夸大为
   所有规模都明显加速。
3. 矩阵路径与基线的第一候选、第二候选和接受结果完全一致；分数误差最大为
   `5.96e-8`，来自浮点矩阵运算，不改变判定结果。
4. 多帧实验选择了“5 帧中选择人脸区域最清晰的一帧”。在身份互斥的独立验证集上，最差场景的
   端到端正确接收率从单帧 `82.86%` 提升到 `100%`，未知人员误接收率从 `0%` 变为 `0%`，
   达到预先规定的至少 1 个百分点收益门槛，因此接入摄像头运行时。
5. 本地图片仍然只提取和识别一帧；摄像头点击识别时采集 5 帧，相邻采集间隔 80 ms。多帧只
   处理短时间内的偶发模糊、曝光或距离变化，不代表解决极端低质量人脸。
6. 识别页和标准库页已拆分为独立页面，使用深色双栏工作区；离屏视觉检查覆盖未启动、识别成功、
   未知人员、标准库异常和人员详情五种状态。

## 2. 标准库矩阵实现

新增 `InMemoryFaceLibrary` 和 `FaceLibrarySnapshot`。快照包含按人员编号排序的身份列表和连续的
`P × 512` `float32` 矩阵，其中 `P` 是身份数。查询向量与矩阵相乘得到所有人员分数，再用两次
`argmax` 找第一和第二候选；不做完整排序，也没有引入近似索引。

更新流程是复制后替换快照：识别线程只读取任务开始时取得的不可变快照，录入线程完成后只刷新
受影响人员对应的标准库行。人员平均特征向量没有写入数据库，数据库仍只保存原始样本及其哈希，因此重启后可以从
原始数据恢复。

完整性检查不再位于每一次识别的热路径中，而是发生在：

- 程序启动时；
- 新增人员或追加样本成功后；
- 操作者点击“重新检查标准库”时。

检查失败会清空内存矩阵、禁用识别和录入，但保留“重新检查标准库”按钮作为恢复入口。系统不承诺
监视进程外部对数据库或图片的实时修改。

## 3. 完整链路性能实验

### 3.1 实验条件

实验命令：

```bash
.venv/bin/python scripts/benchmark_runtime_pipeline.py \
  --data-dir ./data \
  --protocol ./data/experiments/phase4/protocol.json \
  --lfw-root ./data/datasets/lfw_funneled \
  --cache ./data/logs/cache/lfw_raw.sqlite \
  --output-dir ./data/experiments/phase5c/runtime-performance \
  --scales 3,10,100,1000,4588 --query-count 30 --warmup-count 5
```

数据来自自然 LFW，随机种子为 `2026`；每个规模固定 30 张待识别图片，先预热 5 次。脚本使用
真实图片读取和 `FaceEngine`，从 150 张固定候选图片中准备出 30 张可用于比较的图片，8 张因检测到
多人脸而被拒绝。当前这次性能运行环境报告的实际模型后端是 CPU；应用仍保留 CUDA 优先、CPU 回退
的路径，不能根据一次 CPU 报告声称 CUDA 性能。

这里的“中位数”是把 30 次耗时排序后位于中间位置的数，记作 `p50`；“95% 分位耗时”是排序后
约 95% 的样本不超过的延迟，记作 `p95`。它们分别表示典型一次体验和偏慢尾部，而不是两个额外
的算法参数。

### 3.2 完整链路结果

| 标准库身份数 | 基线中位数 | 矩阵路径中位数 | 基线 95% 分位 | 矩阵路径 95% 分位 | 矩阵路径含启动成本的中位数 | 30 次总耗时：基线→矩阵 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 3 | 287.963 ms | 287.598 ms | 304.873 ms | 304.485 ms | 287.612 ms | 8,622.4 → 8,611.6 ms |
| 10 | 289.535 ms | 287.599 ms | 305.315 ms | 304.481 ms | 287.670 ms | 8,643.9 → 8,613.3 ms |
| 100 | 293.634 ms | 287.618 ms | 310.573 ms | 304.501 ms | 288.248 ms | 8,792.4 → 8,630.7 ms |
| 1,000 | 367.272 ms | 289.156 ms | 391.326 ms | 305.353 ms | 295.835 ms | 11,025.8 → 8,826.1 ms |
| 4,588 | 566.103 ms | 288.430 ms | 584.824 ms | 304.834 ms | 320.000 ms | 17,029.4 → 9,587.9 ms |

“含启动成本”把一次性的完整性检查和矩阵构建平均分摊到 30 次查询中。4,588 个身份时，启动
完整性检查为 `885.943 ms`，矩阵构建为 `61.140 ms`，矩阵占用 `9,396,224` 字节，约 `8.96 MiB`。
30 次工作负载总耗时下降约 `43.7%`。但所有规模都由人脸模型推理主导，4,588 个身份时一次
矩阵检索的中位数仍只有 `0.603 ms`，所以本优化的主要收益是消除重复数据库和 Python 逐人处理，
不是加速 InsightFace 模型。

### 3.3 等价性检查

5 个标准库规模各使用同一批 30 张待识别图片。每个规模的第一候选身份、第二候选身份和接受结果
均与基线相同；跨全部规模的最高第一候选分数和第二候选分数绝对误差均不超过 `5.96e-8`。
这满足工程要求的 `1e-6` 误差上限，因此矩阵接入没有改变识别规则。

原始 JSON 和分阶段计时位于：

- `data/experiments/phase5c/runtime-performance/baseline_report.json`；
- `data/experiments/phase5c/runtime-performance/optimized_report.json`；
- `data/experiments/phase5c/runtime-performance/comparison_report.json`。

## 4. 多帧识别实验

### 4.1 实验数据与方法

实验命令：

```bash
.venv/bin/python scripts/evaluate_multiframe.py \
  --phase3-protocol ./data/experiments/phase3/protocol.json \
  --measurements ./data/experiments/phase3/measurements.sqlite \
  --raw-cache ./data/logs/cache/lfw_raw.sqlite \
  --phase4-protocol ./data/experiments/phase4/protocol.json \
  --output-dir ./data/experiments/phase5c/multiframe --seed 2026
```

实验复用阶段 3 已缓存的人脸特征向量和五项原始指标，不重复运行 InsightFace。它把同一身份的
单张输入组织成 5 个位置的模拟短序列，因此验证的是“已有帧质量指标能否选择更好的帧”，不是
摄像头原始视频的现场测量。参数选择集包含 81 个已登记身份和 200 个未知身份；独立验证集包含
35 个已登记身份和 100 个未知身份，身份互斥。

比较方法为：

- 单帧：5 个位置分别单独作为输入，报告其中最差情况，避免只挑最好一帧；
- 清晰度最高帧：在人脸区域拉普拉斯方差最大的有效帧中选择一帧；
- 特征最一致帧：选择与其余有效帧平均余弦相似度最高的帧，同分时选更清晰者；
- 有效帧平均特征：对有效单位向量求平均并重新归一化，显示最清晰的代表画面。

序列场景覆盖轻度综合变化、短暂模糊、明暗波动、人脸尺寸变化和混合变化。固定阈值为阶段 5B
的 `0.5557855367660522`，实验没有为多帧方法重新调参。

### 4.2 参数选择集结果

| 方法 | 五类场景最差端到端正确接收率 | 五类场景最高未知误接收率 |
| --- | ---: | ---: |
| 单帧 | 79.01% | 1.00% |
| 清晰度最高帧 | 97.53% | 1.00% |
| 特征最一致帧 | 97.53% | 1.00% |
| 有效帧平均特征 | 97.53% | 1.00% |

三种多帧方法的统计结果相同。按预先约定的同分优先级，选择实现最简单、计算代价更低的“清晰度
最高帧”。

### 4.3 身份互斥独立验证集结果

| 方法 | 五类场景最差端到端正确接收率 | 五类场景最高未知误接收率 |
| --- | ---: | ---: |
| 单帧 | 82.86% | 0.00% |
| 清晰度最高帧 | 100.00% | 0.00% |
| 特征最一致帧 | 100.00% | 0.00% |
| 有效帧平均特征 | 100.00% | 0.00% |

清晰度最高帧相对于单帧最差场景提高 `17.14` 个百分点，未知人员误接收率没有上升，满足“独立
验证集提高至少 1 个百分点且不增加未知误接收”的接入门槛。因此运行时固定为点击后采集 5 帧、
间隔 80 ms、跳过无效帧；至少一帧有效即可识别，全部无效返回 `no_valid_frames`。本实验的模拟
序列不包含原始画面，现场摄像头仍属于最终展示阶段的功能复验，不把本实验的百分比当作所有
摄像头条件的保证。

原始多帧报告位于 `data/experiments/phase5c/multiframe/`，包括 `calibration_report.json`、
`evaluation_report.json`、`comparison_report.json` 和 `manifest.json`。

## 5. 界面收尾

界面改动已经提交到 `e95db48`（`style: redesign desktop recognition workflow`）：

- `ui/workers.py`：摄像头、识别和录入线程；
- `ui/recognition_page.py`：摄像头控制、实时预览和抓拍结果双栏工作区；
- `ui/library_page.py`：人员搜索、样本数量、来源和缩略图；
- `ui/theme.py`：深色主题；
- `ui/main_window.py`：只负责页面、线程、仓库和内存标准库的协调。

离屏截图检查了以下状态：未启动、识别成功、未知人员、标准库完整性异常、人员详情。停止预览
会清除实时标签中的最后一帧；识别结果显示在右侧独立区域，不会覆盖实时预览。
