# 人脸比对系统需求分析

本文是本项目的需求分析基线，也是课程设计报告“需求与技术现状分析”部分的素材。它区分任务书要求、当前实现、后续计划和系统局限性，不把尚未完成的方案写成已经实现的功能。

## 1. 问题定义

本项目面向外置摄像头和本地图片输入，构建一个离线运行的人脸开放集 1:N 识别系统。系统需要从输入图像中检测人脸、提取特征向量，在本地标准库中搜索候选身份，并根据相似度证据输出已知人员姓名或“未知人员”。

与简单的两张图片 1:1 比对不同，本系统的查询对象是一个 Probe，标准库中可能存在多个 Identity，每个 Identity 还可能有多张 Reference Sample。因此系统需要同时处理：

- 摄像头帧与本地图片的统一输入；
- 无脸、多人脸、脸过小、模糊和暗光等无效输入；
- 多身份 Gallery 中的 1:N 搜索；
- 同一身份多样本的分数聚合；
- 分数不足或候选不明确时的 Unknown 拒识。

## 2. 使用者与使用场景

### 2.1 操作者

操作者通过桌面 UI 完成设备选择、预览、抓拍、本地图片识别、人员创建、样本追加和结果查看。课程展示时，操作者还需要能够解释系统的数据流、算法、阈值和测试结果。

### 2.2 被识别对象

被识别对象不直接操作系统，只作为摄像头前的人或本地图片中的人脸出现。其身份可能已经存在于 Gallery，也可能属于 Unknown。

### 2.3 主要场景

1. 启动程序并加载本地模型和标准库；
2. 刷新并选择外置摄像头，查看实时预览；
3. 抓拍当前画面并进行 Known/Unknown 判断；
4. 选择本地图片作为 Probe 进行识别；
5. 从摄像头或本地图片创建新人员；
6. 为已有人员追加不同来源、角度或质量的样本；
7. 查看人脸框、相似度、候选差距、耗时和异常原因；
8. 重启后继续使用已有 Gallery。

## 3. 功能需求

| 编号 | 需求 | 输入 | 输出/结果 | 当前状态 |
| --- | --- | --- | --- | --- |
| F-01 | 调用外置摄像头并支持拍照 | 摄像头设备索引、视频帧 | 实时预览、抓拍帧、设备异常提示 | 已实现并完成 Phase 1 验收 |
| F-02 | 建立不少于 3 个身份的标准库 | 人员名称、至少 1 张有效图片 | 人员记录、样本图片、embedding | 已实现；最终 Demo Gallery 待后续建立 |
| F-03 | 完成人脸开放集 1:N 判别 | Camera/File Probe、Gallery | 姓名和相似度，或 Unknown | 已实现；阈值和聚合仍需后续实验 |
| F-04 | 提供清晰、简洁、友好的 UI | 操作者按钮和文件选择 | 预览、检测框、结果和异常反馈 | 基础功能已实现；视觉收尾仍需后续处理 |
| F-05 | 支持标准库动态扩容 | 新人员图片、已有人员追加图片 | 新增内容立即参与后续比对 | 已实现并完成 Phase 1 验收 |

基础功能的验收重点是完整链路可运行，不要求所有低质量图像都被强行识别；质量不足时明确拒绝属于正确行为。

## 4. 扩展功能需求

任务书将扩展功能列为基础功能之外的加分项，并列出鲁棒性优化、检测与比对时间优化等方向。本项目的开发计划同时纳入两个可分别验证的扩展，并将实现范围限定在课程时间和本地 CPU 能力可完成的内容：

- 鲁棒性扩展：短时间窗口内采集多帧，利用已有质量指标选择较可靠的帧，再进行识别；
- 时间扩展：以端到端处理时间为对象，记录输入准备、检测、质量检查、特征提取、标准库检索、判定、日志和界面反馈等阶段的总耗时，定位主要耗时环节后实施小范围优化；
- 验证方式：分别比较单帧与多帧质量择优、优化前与优化后的端到端流程，固定模型、Gallery、阈值、硬件和测试数据，报告成功率、拒识率、分阶段耗时、总耗时和功能代价；
- 备选分析：如时间允许，再比较不同人员多样本聚合方式，分析准确性和计算代价；它不是本阶段必须完成的扩展；
- 不把极端暗光、严重模糊、强遮挡、极端侧脸、远距离小脸和支付级安全当作本课程必须解决的问题。

扩展必须保留优化前基线、问题证据、优化方案、相同条件复测结果、收益和代价。

## 5. 数据需求分析

### 5.1 输入数据

- `camera`：OpenCV 读取的 BGR 视频帧，来自外置摄像头；
- `file`：操作者选择的本地图片；
- `dataset`：只用于开发、算法比较和评测的数据集图片。

三种输入都经过同一套人脸检测、质量检查和特征提取逻辑。Probe 被识别后不会自动写入 Gallery。

### 5.2 Gallery 数据

每个 Identity 至少有一个有效 Reference Sample。样本包含：

- 人员标识和展示名称；
- 样本图片路径和来源；
- `float32` embedding 及向量维度；
- 检测分数、脸部尺寸、清晰度、亮度、对比度和质量等级；
- 图片哈希和 embedding 哈希；
- 创建时间及样本编号。

图片和向量是一一对应的。图片用于复核和重新处理，向量用于在线比对；当前系统不保存固定身份模板，查询时与该身份的所有样本计算分数，再进行人员级聚合。

### 5.3 配置和日志

配置保存匹配阈值、候选差距、Top-K 和质量规则。识别日志保存时间、决策、人员、最高分、第二候选分数、耗时和异常原因，用于问题定位与实验复现。

## 6. 核心业务规则

1. 标准库录入图片必须检测到恰好一个可信人脸；无人脸、多人脸、脸过小或质量不足时拒绝；
2. 新人员只要有一张有效样本即可参与识别，不固定姿态、动作、数量或采集顺序；
3. 同一人员允许追加多张图片，图片质量可以不同；多样本不是入库门槛；
4. Query 与每个人的全部有效样本计算余弦相似度，再按当前聚合规则得到人员分数；
5. 最佳人员分数和候选差距同时满足当前策略时输出姓名；否则输出 Unknown；
6. 输入质量不足或标准库完整性失败时输出 Invalid，而不是把它混同为 Unknown；
7. 标准库至少需要 3 个不同身份才能满足课程基础功能要求，但开发、调参和最终演示数据必须分开管理；
8. 标准库被识别时只读取本地数据，不访问网络。

## 7. 人机交互需求

- 首页能够看到当前设备、预览状态和可执行操作；
- 预览启动、停止、故障和重开状态清晰可见；
- 停止预览后不保留容易误认为实时画面的最后一帧；
- 识别结果至少显示检测框、姓名或 Unknown、相似度、候选差距、耗时和原因；
- 标准库页面显示人员和样本数量；
- 新增和追加操作明确区分摄像头帧、本地图片和失败原因；
- 设备打不开、图片无法解码、多人脸、低质量和标准库损坏时给出可理解的反馈；
- UI 不因模型推理、数据库写入或摄像头读取而长时间冻结。

## 8. 非功能需求

### 8.1 可运行性

当前项目选择 Python 源码运行，不制作 EXE。运行目标为支持 Python 3.11～3.13 的 Windows、Linux 和 macOS；识别使用本地 InsightFace 模型和 CPUExecutionProvider。

### 8.2 离线与数据边界

模型准备阶段可以联网下载，正常启动和演示只使用本地模型。标准库图片、向量和日志保存在本地 `data/`，不上传外部服务。

### 8.3 可靠性

人员及样本使用原子事务写入；图片与向量分别保存哈希；识别前执行 SQLite、外键、图片和向量完整性检查。摄像头和推理错误需要转化为 UI 可见状态，而不是导致程序崩溃。

### 8.4 可维护性与可复现性

采集、检测、质量、特征、标准库、识别和 UI 分模块组织；实验输入、协议、参数、逐样本结果和汇总指标应能够被重新运行。源码函数和关键步骤使用统一中文注释。

## 9. 技术现状与项目边界

当前采用 InsightFace `buffalo_l` 完成人脸检测和 embedding 提取，OpenCV 负责摄像头/图片输入，PySide6 负责桌面 UI，SQLite 负责本地持久化。该技术组合可以完成课程要求的主链路，但当前默认阈值和 Top-K 质量加权规则尚未经过独立 Calibration/Evaluation 身份划分的正式标定。

以下问题作为系统局限性，不在当前课设范围内承诺完全解决：

- 极端暗光、严重运动模糊、强遮挡或极端侧脸造成身份信息不可见；
- 远距离小脸、低分辨率监控和跨摄像头域迁移；
- 面向所有年龄、肤色、设备和环境的统一准确率保证；
- 活体检测、照片/屏幕重放防护和支付级安全认证；
- 大规模身份库、分布式存储和高并发服务化部署。

## 11. 工程结构说明

`src/` 是源码隔离目录；`src/camera_face_comparison/` 是可导入的 Python 主包，负责应用业务模块；其下的 `ui/` 是界面子包。根目录的 `pyproject.toml` 提供安装配置和命令入口，因此根目录不需要额外放置 `main.py`。

`src/camera_face_comparison.egg-info/` 不属于源码结构，是 `pip install -e .` 自动生成的安装元数据，已被 Git 忽略，提交源码时不应包含。
